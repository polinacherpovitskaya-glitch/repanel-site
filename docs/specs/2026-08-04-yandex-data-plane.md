# RePanel site: единый контур данных в Yandex Cloud

Дата: 2026-08-04

## Контекст

Сайт RePanel сейчас разделяет данные между двумя провайдерами:

- каталог, промокоды и файловое хранилище находятся в Supabase;
- заказы, история заказов, возвраты и сертификаты находятся в YDB;
- приложение работает в Yandex Serverless Containers, а основные домены на
  Vercel перенаправляют посетителей на российский адрес `site.re-panel.ru`.

Это усложняет резервное копирование, эксплуатацию и контроль местонахождения
данных. Основные пользователи и сотрудники находятся в России, поэтому рабочий
контур должен оставаться доступным без VPN и хранить данные в российском ЦОД.

## Цель

Перенести все рабочие данные RePanel site в единый изолированный PostgreSQL в
Yandex Cloud, а изображения — в Yandex Object Storage. Запустить приложение на
существующей российской VM за Caddy, сохранив Vercel только как разрешённый
редирект/preview-контур.

После переключения runtime приложения не должен требовать Supabase или YDB.

## Архитектура

### Приложение

- Next.js standalone-контейнер на существующей VM RePanel в Yandex Cloud;
- отдельный непривилегированный пользователь контейнера, read-only rootfs и
  лимит памяти;
- доступ к приложению только через Caddy по внутренней Docker-сети;
- сначала теневой адрес, затем `site.re-panel.ru`;
- `/api/health` сообщает версию, доступность БД и режим запрета записи, но не
  раскрывает секреты.

### PostgreSQL

- отдельная база `repanel_site` и отдельная роль только для этого приложения;
- одна таблица документов `site_records(collection, id, body, created_at,
  updated_at)` с `jsonb`-телом: формат сохраняет исходные записи без потери
  полей и совместим с уже используемой адаптерной моделью YDB;
- допустимые коллекции перечислены явно;
- уникальные индексы защищают `products.slug`, `certificates.code` и
  `promo_codes.code` от дублей;
- все операции выполняются только серверным модулем; строки подключения и
  административные ключи не попадают в браузер и сборку.

### Объектное хранилище

- отдельный бакет Yandex Object Storage для изображений товаров;
- загрузка выполняется только защищённым административным route handler;
- публичный URL сохраняется в карточке товара;
- бакет и резервный бакет имеют версионирование.

## Совместимость приложения

- бизнес-роуты и административные страницы сохраняют текущие URL и JSON-ответы;
- серверный адаптер поддерживает реально используемые операции `select`,
  `insert`, `update`, `delete`, `eq`, `neq`, `in`, `ilike`, `order`, `limit`,
  `single`, `maybeSingle` и точный `count`;
- серверные страницы каталога читают PostgreSQL напрямую;
- клиентская корзина получает опубликованные товары через собственный
  read-only API, поэтому публичные Supabase URL и anon key больше не нужны;
- текущий режим магазина «скоро» не меняется этой миграцией.

## Перенос и сохранность данных

До любого переключения обязательны:

1. полные экспортные копии Supabase и YDB с манифестами, количеством записей и
   SHA-256;
2. загрузка архивов в приватный версионируемый бакет Yandex Object Storage;
3. контрольное скачивание архивов и повторная проверка SHA-256;
4. импорт всех десяти логических коллекций в PostgreSQL;
5. сравнение количества и канонических хэшей каждой коллекции;
6. резервная копия целевой базы после импорта и пробное восстановление в
   отдельную временную базу;
7. финальная дельта после краткой блокировки старого write-path;
8. smoke-тесты чтения и обратимых тестовых записей на теневом контуре.

Удаление данных или ресурсов Supabase/YDB не входит в этот этап. Старый контур
остаётся доступным для отката в режиме без новых записей минимум 14 дней.

## Переключение

1. Проверить теневой адрес из России и извне.
2. Зафиксировать финальные экспорты и остановить старый write-path.
3. Применить дельту и снова сверить хэши.
4. Переключить `site.re-panel.ru` на VM и сохранить редиректы Vercel.
5. Проверить TLS, главные страницы, каталог, административный вход, API оплаты
   без создания реального платежа и чтение двух существующих заказов.
6. Наблюдать ошибки, БД, бэкапы и доступность 14 дней.

Откат выполняется возвратом домена на прежний Yandex Serverless Container.
Никакие исходные данные для отката не удаляются.

## Приёмка

- все исходные записи присутствуют в PostgreSQL и совпадают по каноническим
  хэшам;
- восстановленная из бэкапа временная база даёт те же количества и хэши;
- приложение собирается и проходит lint/тесты;
- в клиентских JS-артефактах нет Supabase URL, anon key или YDB-конфигурации;
- production runtime не содержит переменных Supabase/YDB;
- сайт и административная панель открываются из российского контура без VPN;
- старый контур сохранён для отката и не принимает новые записи;
- ежедневная резервная копия PostgreSQL подтверждена контрольным скачиванием.

## Вне рамок

- изменение дизайна и логики магазина;
- включение магазина из режима «скоро»;
- удаление Supabase, YDB или Yandex Serverless Container;
- перенос Vercel-редиректов;
- рефакторинг платежной интеграции Точки или доставки СДЭК.
